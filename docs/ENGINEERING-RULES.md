# قواعد الهندسة الملزمة — نظام الوكالة

هذا الملف ليس توثيقاً للقراءة، بل **قائمة شروط قبول**. كل قاعدة هنا دُفعت
ثمنها من عيب حقيقي وصل إلى جهاز، لا من مقالة قرأناها.

---

## القاعدة الأولى: البناء الأخضر لا يعني أن التطبيق يعمل

### الحادثة التي أنتجت هذه القاعدة

كان الـ CI أخضر، والـ APK يُنتَج ويُرفع بنجاح، وتقرير الاختبارات يُنشر.
ثم ثُبِّت الـ APK على جهاز حقيقي فظهر **دوّار تحميل لا ينتهي أبداً**.
لم يكن الدوّار صورة تجميد: كان قفلاً مُتبادلاً حقيقياً في الكود.

```kotlin
// الحالة الابتدائية
var session = SessionState.Loading

// ولا تخرج منها إلا بـ bootstrap() …
LaunchedEffect(Unit) { onBootstrap() }   // في LoginScreen

// … لكن LoginScreen لا تُركَّب إلا بعد SignedOut
when (session) {
    Loading -> FullScreenLoading()
    SignedOut -> LoginScreen(...)   // ← لا تُبنى قبل انتهاء Loading
}
```

كل طرف كان ينتظر الآخر. النتيجة: تطبيق لا يفتح، وبناء أخضر تماماً.

### لماذا لم يكشفه أي شيء في الـ CI

| الأداة | لماذا فشلت في الكشف |
|---|---|
| `:app:assembleDebug` | يترجم ولا يشغّل |
| `:app:testDebugUnitTest` | يختبر المستودعات لا دورة حياة الواجهة |
| `connectedAndroidTest` | لم يكن موجوداً في الـ workflow |
| `lint` | لا يرى ترتيب تركيب الـ Composables |

السبب الجذري: **الكمبيوتر يثبت أن الكود يُترجم، لا أنه يُستعمل.**

### القاعدة المستخلصة

> **كل تسليم يُثبَّت ويُشغَّل قبل أن يُعلَن.**

الشروط الأربعة الدنيا لأي إعلان إنجاز:

1. `BUILD SUCCESSFUL` + `testDebugUnitTest` أخضر.
2. **تثبيت فعلي** للـ APK على جهاز/محاكي.
3. **تشغيل فعلي** يصل إلى الشاشة الأولى، و**قراءة الشاشة** (لا الاكتفاء بأن العملية حيّة في الخلفية — `pidof` يُظهر عملية حتى لو كانت عالقة).
4. **مسار مستخدم واحد كامل** يُنفَّذ بالنقر الحقيقي حتى نهايته.

وبلا ذلك: تُقال الحقيقة بلفظها — «يبني ولا يُثبت أنه يعمل».

### الأخطاء الفرعية التي وقعنا فيها ونحن نتحقق

التحقق نفسه له فخاخ، وهي مسجّلة هنا لأنها تضيّع الوقت:

- **`pidof` ليس دليل حياة.** العملية كانت موجودة والشاشة دوّار.
- **`dumpsys activity` قد يُظهر تطبيقنا في المقدمة وهو فارغ.** تحقق من المحتوى.
- **`screencap` يلتقط ما على الشاشة، وقد يلتقط تطبيق الأداة نفسها** لأن تنفيذ
  الأمر يُعيد التركيز إليها. لذلك: التحقق النصي عبر `uiautomator dump` ثم
  فلترة `package=` هو المرجع، والصورة تأكيد ثانوي.
- **`input tap` بإحداثيات محسوبة يدوياً هشّ.** عند فتح لوحة المفاتيح ينزاح
  التخطيط بمقدار ~195px فتصيب النقرة حقلاً آخر. الحل الموثوق:
  `KEYCODE_TAB` للانتقال بين الحقول بدل حساب الإحداثيات.
- **`input text` قد يُسقط محرفاً أو يُضيف مسافة.** قِس النتيجة برمجياً قبل
  المتابعة، ولا تفترض. `wc -m` على نص الحقل يكشف الفرق بين 10 و11 محرفاً.
- **أخطاء الحقن (`Dagger/MissingBinding`) لا يمسكها أي فحص ساكن للاستيرادات.**
  بعد فشل Dagger مرة على `@ApplicationContext`، فحصنا الملفات آلياً بحثاً عن
  رموز بلا `import` فوجدنا نتيجتين كلتاهما **إيجابية كاذبة**. الفحص الساكن
  يقلّل الاحتمالات، ولا يغني عن بناء حقيقي.

### حارس آلي يمنع تكرار العطب

`BootFlowGuardTest` يقفل السلوك المكسور تحديداً: يثبت أن الحالة الابتدائية
`Loading`، وأن `bootstrap()` ينقلها **حتى لو لم تُركَّب أي شاشة**، وأن الفشل
يهبط إلى `SignedOut` لا إلى انتظار أبدي. أُضيف ليصير العطب مستحيلاً بالرجوع.

## القاعدة الثانية: الحالة لا يحرّكها إلا من يملكها

كل تدفق `StateFlow` يجب أن يكون له **مالك واحد** مسؤول عن نقله من حالته
الابتدائية. القفل المُتبادل أعلاه حدث لأن المالك (`bootstrap`) رُبط بمسار
واجهة يعتمد على نتيجته. القاعدة: **التهيئة تُستدعى فوق نقطة التفريع، لا
داخلها**. وكل تهيئة تُلفّ بـ`runCatching` يهبط إلى حالة صالحة، لأن الحالة
الابتدائية هي دائماً الأخطر: إن لم يُكتب فيها شيء، بقيت الواجهة معلّقة.

---

## القاعدة الثالثة: الفشل يُعلَن، لا يُخفى

- التشفير في `SecureStore` له مسار انحدار، لكنه **مكشوف** عبر `isEncrypted`
  بدل أن يكون صامتاً.
- `SyncSocketClient` يتجاهل رسالة واحدة تالفة بدل إسقاط الحلقة، **ويُسجِّل**.
- `ReportRange` كانت زخرفية تُوهم بفلترة غير موجودة، فأُعطيت `days` حقيقية.
- ما لا يُنفَّذ يُكتب في التقرير كدَين: الشاشات الناقصة، الاختبارات الغائبة،
  الحركات المؤجلة.

---

## القاعدة الرابعة: الرقم يُقاس لا يُتذكَّر

في تقرير واحد صُحِّحت أرقام كنت أحملهما في الذاكرة: عدد المسارات المسجّلة
(19 لا 20)، وعدد أسطر ملف (285 لا 300). الرقم المحفوظ يتقادم بصمت، والرقم
المقاس يُكذّب نفسه بنفسه. لذلك كل تقرير يبدأ بأوامر قياس، ويُنشر ناتجها.

## قائمة تحقق ما قبل كل إعلان إنجاز

```
[ ] git status نظيف، والـ commit مدفوع
[ ] Actions: completed / success
[ ] :app:testDebugUnitTest نُفِّذ فعلاً (لا NO-SOURCE)
[ ] APK مُنزَّل من الـ artifact، الحجم معقول
[ ] التثبيت نجح (pm install → Success)
[ ] الشاشة الأولى قرأنا نصوصها فعلياً (uiautomator dump)
[ ] مسار مستخدم واحد أُكمل حتى نهايته بالنقر الحقيقي
[ ] ما لم يكتمل مكتوب صراحةً في التقرير
```

أي بند بلا علامة يعني: لا يُقال «تم».
